# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Salesforce test-data generator. Users build a workflow of nested steps in the browser (the "Quy trình" view: Record / Loop / Branch steps, Power Automate style; or the auto-laid-out, pan/zoom "Sơ đồ" view of the same tree, key M), the UI POSTs the **workflow JSON** to a Node.js server, and the server generates Salesforce-typed values and can insert them into an org. Org credentials come from the **locally installed, authenticated `sf` CLI**, and are never stored.

Stack constraint: Node.js and plain HTML/JS (ES modules, no build step). Add React or Tailwind only if they are really needed. The only runtime dependency is **jsforce** (Salesforce API), so run `npm install` once.

## Commands

```bash
npm start                                  # server + UI on http://127.0.0.1:3000 (PORT, HOST env vars)
```

## Architecture (read docs/architecture.md for detail)

- **The workflow JSON is the contract** between client and server (`docs/workflow-schema.md`). It is a tree since design 0003: `version: 2`, `steps[]`, child sequences in `slots` (loop `body`; branch `true`/`false`), optional `disabled`; no edges or positions. A change to step types, slots, config keys, field types or option schemas must update `server/workflow/nodes.js` or `server/generators/*`, `server/workflow/schema.js`, the executor, docs and tests together. The table in `.claude/agents/implementer.md` lists every layer.
- **The server is the single source of truth for options.** Generators (`server/generators/`) and step types (`server/workflow/nodes.js`: `slots`, `category`, `options`) declare their schemas. `GET /api/meta` serves them, and `client/js/forms.js` renders the forms from them. Don't hard-code per-type options in the client.
- **The executor (`server/workflow/executor.js`) is pure and streams** (design 0004, always on). `createRun(workflow, { seed, now, queryResults })` validates once; its `records()` is a synchronous generator yielding records in generation order (parents before children), a fresh run on each call; `runWorkflow` just collects it (tests, JSON response). `server/run.js` drives the sinks: a preview / dry pass (counts, first `LIMITS.previewRows` per sObject; a generation error stops before any write), then for an org target a second identical pass into the windowed inserter; it yields the event loop, throttles progress and honours the cancel signal. `/api/run` streams NDJSON events with `Accept: application/x-ndjson` (plain JSON otherwise); `POST /api/runs/:id/cancel` stops a run; `POST /api/export` regenerates CSV/JSON from seed + now. Record pools are count-only unless a step reads whole records of them (`poolUsage` in `shared/scope.js`: step options `kind: 'ref'` with `accepts.pool`), so memory does not grow with the record count. `runSteps` walks `steps` top to bottom. Loop runs `slots.body` N times (N may come from a number variable, `count: "{{acc.N}}"`, design 0013; or, with `mode: 'each'` of design 0010, once per record of the pool `from` snapshotted when the loop starts, in pool order, without the rng — design 0013 adds an optional filter, `order: 'shuffle'` (draws exactly k numbers) and `limit` —, the record bound as `scope.current[itemAlias]` inside the body only; or, with `mode: 'values'`, once per value of a fixed list as `{{loop.value}}`), Branch runs `slots.true` or `slots.false` (`right` may hold `{{…}}`), and both then continue with the next step. `scope.run` holds `{{run.seed}}`, `{{run.now}}`, `{{run.today}}` (meta `globals`). Query (design 0006) never calls the org: the server reads every enabled Query step first (`server/sf/query.js`, jsforce `conn.query`, cached 10 min, fingerprinted; sample rows without an org) and passes the rows as `opts.queryResults`; the step binds them as a pool of `existing` records (real Ids, no current record). Pick (Chọn bản ghi) chooses one record of a pool with the seeded rng. `disabled` steps (and their children) are skipped without touching the rng. Results include `stats.byStep`. Record pools (`scope.current/all`) are global to the run; loop vars (`scope.vars`) are lexical.
- **Shared modules (`shared/`)** are pure ES modules used by both server and browser (served at `/shared/`): `workflow-tree.js` (tree operations), `migrate-v1.js` (v1 graph → v2 tree), `soql.js` (Query SOQL building/checks, read-only SELECT only), `scope.js` (`analyzeScope`, design 0005: the single variable-scope analysis, driven by each step type's `flow`/`exposes`; used by server validation and, in the browser, by the variable picker, the Lookup `ref` dropdown and reference-following renames). The server still accepts v1 workflows and migrates them before validating; the client migrates v1 autosaves/files and never overwrites `sfdg.workflow.v1`.
- **Determinism:** all randomness goes through the seeded `ctx.rng` (`server/random.js`), and all time through `ctx.now`. Never use `Math.random` or `Date.now` in generators or the executor, because preview-then-insert with the same seed and `now` relies on it (the insert and `/api/export` re-run the preview's seed + now; `test/stream.test.js` pins the records to golden hashes).
- **Org access is split in two:** `server/sf/cli.js` only shells out to `sf org list` / `sf org display` to get orgs, an access token, an instance URL, the username and the org Id. Every Salesforce API call goes through a **jsforce `Connection`** in `server/sf/client.js`, one per CLI identity (instance URL + username + org Id). `client.whoami` checks who the connection really is (org and user Ids parsed from the REST root's `identity` URL, never fetched, so the token never goes to login.salesforce.com; the username from one `User` query) and returns a `session`; inserts and deletes pass that session instead of the alias, so every `create` / `destroy` / `bulkJob` stays on the checked connection. Its `refreshFn` asks the CLI for a fresh token on `INVALID_SESSION_ID` and fails closed: a token of another org or user is refused and the run stops with `stopped.reason: 'orgChanged'`. Add new API features on that connection, not with hand-written `fetch` calls (`test/safety.test.js` scans for this). Bulk API 2.0 is `client.bulkJob`, `insert` / `delete` only; `client.query` (REST `/query`, never `queryAll`) is the read path.
- **Lookups** are emitted as `{ "$ref": "alias#n" }`. `server/sf/insert.js` (`createInserter`) resolves them by inserting each window of 2 000 streamed records in dependency "waves" through `conn.sobject(type).create(records, { allOrNone: false })` (sObject Collections, at most 200 records per call), keeping only the Ids later records need; it stops after the first 3 calls of an sObject all fail, and groups errors. A Record step whose alias no Lookup needs and that creates at least `LIMITS.bulkMinRecords` records goes through Bulk API 2.0 after a Collections probe (`planInsert` in `shared/insert-plan.js`, also used by the confirmation dialog). The Ids of every call or job are appended to insert history (`server/history.js`, under `SFDG_DATA_DIR`, one server per data directory via a lock file, files 0600, no tokens) before the next write; a failed append stops the run. `server/sf/delete.js` deletes exactly those Ids, children first, after collecting the Ids of Bulk jobs not read yet.
- **Validation issues always carry `nodeId` and `field`** (`nodeId` is the step id; `field` is an option key, `fields.<Name>` or `slots.<key>`), so the UI can badge the step and outline the field or slot. The UI says "bước", not "node". User-facing strings are Vietnamese and should say how to fix the problem.
- **Client state** is in `client/js/store.js`: undo/redo, autosave, and events tagged with a `source`. Autosave goes to the **workflow library** (design 0012 A: `client/js/library.js` storage, `client/js/library-ui.js` UI; `sfdg.library` index + one `sfdg.wf.<id>` key per workflow, the tab's open entry in `sessionStorage`); `sfdg.workflow.v2` / `v1` are only read for the first-run migration and never written or removed (v2 is still the autosave if the library could not be created). Switching workflows (`openWorkflow`) resets undo and run state. The selection is a primary step plus optional `ids` (multi-select, `client/js/selection.js`); copy/paste uses the clipboard format of `client/js/clipboard.js`. The inspector ignores its own `source: 'inspector'` events so typing doesn't lose focus. Structural edits use `'inspector-structure'`. Step operations live in `client/js/ops.js`, the view in `client/js/process.js`, card summaries in `client/js/summary.js`; collapsed frames are UI state (`sfdg.collapsed`, no undo). Insert history and the delete UI live in `client/js/history.js` (the delete itself runs in the results panel via `deleteRun` in `main.js`); the client never sends Ids, only the confirmation. Workflows entering the app (open, file import, paste) go through `normalizeStepIds` (`shared/workflow-tree.js`, `STEP_ID`), because the server refuses invalid step ids.
- **Safety:** the server binds `127.0.0.1` by default because it acts with the local sf CLI's org access (on a wildcard bind, org writes accept only an IP, `localhost` or the machine's own Host). Org writes happen only (1) via `/api/run` with `target.kind === 'org'`, behind a UI confirmation, and only if insert history can be written (503 otherwise, Insert locked in the UI); (2) via `POST /api/history/:hid/delete`, which deletes only the Ids history recorded for that insert, after the server re-checks `confirm.username`, that `confirm.count` equals what is left after reading pending Bulk jobs (else 409 with the new `count`; the UI never re-sends without a new click), that the org behind the alias has the same org Id and username as at insert time, and `typedOrg` for production or unknown-kind orgs. Records go to the Recycle Bin (never `hardDelete`). `LIMITS` in `server/workflow/nodes.js` caps records, executed steps, nesting depth (`maxDepth`), insert history (`historyMaxRuns`, `historyMaxBytes`) and the Bulk thresholds; `MAX_BODY` caps request bodies. Tests never touch a real org: they use `test/fake-salesforce.js` and `SFDG_DATA_DIR` in a temp directory.

## Agents, skills, docs

- Feature work starts with the **`planner`** agent. It focuses on usability and writes a design doc to `docs/design/NNNN-*.md` (skill `design-doc`), checked against the usability principles in `docs/design/README.md`. **`implementer`** builds it, **`field-type-author`** handles generators, and **`reviewer`** checks the diff (read-only).
- Skills: `design-doc`, `add-field-type`, `add-node-type`, `smoke-test` (in `.claude/skills/`).
- `docs/` is written in **Vietnamese**; code, identifiers and this file are in English. When behaviour changes, update the matching doc (`workflow-schema.md`, `field-types.md`, `org-connection.md`) and the design doc's "Đã làm" section.
- The test environment may lack the `sf` CLI. `/api/orgs` then returns 503, and tests mock `cli.run` and the client (`createConnection` is injectable). `test/jsforce.test.js` runs real jsforce against a fake Salesforce on localhost. jsforce ignores `NO_PROXY`, so that file clears the proxy variables before importing it. Never insert into a real org while testing unless the user named that org.

# Add or change a step type

Step types are part of the saved workflow format (`version: 2`, a tree of steps; see `docs/workflow-schema.md`). Never rename an existing `type`, slot key or config key without a migration.

1. **Catalogue** — add the entry to `NODE_TYPES` in `server/workflow/nodes.js`: `type`, Vietnamese `label` and `description`, `category` (`data` or `control`, labels in `STEP_CATEGORIES`), `slots` (`[]` for a plain step; for a container `[{ key, label, empty?, hint? }]` in reading order — the first empty slot is where the default insert rule puts new steps), and `options` in the generator option format (defaults required; `default` is the value used when the key is missing — the executor must fall back to the same value — and `initial`, optional, is what a step added from the UI starts with). Org-dependent steps set `needsOrg: true`; options can ask for org help with `suggest` (design 0006). Mark the options that describe the step with `summary: true` if it has no dedicated summary.
   - **Variables (design 0005):** declare `flow` (`{ kind: 'sequence' }`; `{ kind: 'loop', body: '<slot>' }` plus a `minIterations(config)` function — also register it in `MIN_ITERATIONS` of `shared/scope.js`, since functions are not served by `/api/meta`; `{ kind: 'branch', alternatives: ['<slot>', …] }`) and, if the step provides variables, `exposes` (`kind: 'record' | 'vars'`, `name: { key, default?, fallback? }`, `label`, `visibleIn: 'downstream' | { inside: '<slot>' }`, `members` (`'fields'`, `'select'`, a fixed list or `{ fromSource: '<option>' }`), `builtins` (`$…` keys), `current` (`'last' | 'picked' | 'none'`), `pool`, `origin`, `lookupParent`, `open`). An option that accepts variables declares `vars: 'template' | 'path'`; one that names a source is `kind: 'ref'` (with `accepts: { pool: true }` etc. if not every Lookup parent fits).
2. **Validation** — in `server/workflow/schema.js` validate every config key; push issues with `nodeId` (step id) and `field` (option key, `fields.<Name>` or `slots.<key>`) and a message saying how to fix it. Add a warning (not an error) for legal-but-probably-unintended states (e.g. an empty slot). Turned-off steps are not checked. Anything about "is this variable usable here" goes through `analyzeScope` in `shared/scope.js`: every option with `vars` or `kind: 'ref'` is checked automatically, and the messages for each `code` live in `referenceIssue` (`schema.js`).
3. **Execution** — add a `case` in `runSteps` in `server/workflow/executor.js`. Keep the executor pure (no I/O). Use `rng` for any randomness and keep the rng call order stable. Respect `LIMITS` and count steps. Lexically scoped variables go in `scope.vars`; record pools (`scope.current`, `scope.all`) are global for the run. Fill `stats.byStep[step.id]`.
4. **Shared** — `shared/scope.js` reads `flow`/`exposes`, so a step type that fits those kinds needs no change there (new loop types: `MIN_ITERATIONS`, and `VAR_EXAMPLES` for the picker's example values). `shared/workflow-tree.js` works from the slot list in meta; renames follow every option with `vars` / `kind: 'ref'` when given the catalogue.
5. **UI** — colours and icon (design system, `docs/ui-design-system.md` §3.4, §5, §10; never hard-code colours in JS):
   - pick an OKLCH hue at least 35° away from the hues in use (not the accent or a status hue) and rerun the contrast + colour-blind check of design doc 0008;
   - in the token block of `client/css/app.css` add the primitives (`--<family>-50/100/600/700` for light, `-300/200` for dark), the four tokens `--step-<type>`, `--step-<type>-subtle`, `--step-<type>-strong`, `--step-<type>-text` in the light block **and in both dark blocks** (`@media (prefers-color-scheme: dark) :root:not([data-theme="light"])` and `:root[data-theme="dark"]`), and an icon `--ico-<type>` (24×24 SVG, stroke 2, as a `data:` URL);
   - below `/* ===== end tokens ===== */` add one `[data-type="<type>"]` rule setting `--c`, `--c-subtle`, `--c-strong`, `--c-text` and `--ico`. The JS only sets `data-type="<step.type>"` and inserts `icoTile()` (`client/js/dom.js`), which process view, palette, "+" menu and inspector already do;
   - update the tables in `docs/ui-design-system.md` (§2 primitives — `test/css-tokens.test.js` compares it with the CSS —, §3.4, §5, §8.1);
   - add a summary in `stepSummary` and a chip in `statChip` (`client/js/summary.js`). The process view draws frames and columns from `slots` automatically.
6. **Docs** — update the step table and semantics in `docs/workflow-schema.md`.
7. **Tests** — executor semantics and validation errors in `test/workflow.test.js`; scope (what the step exposes, where it is visible) in `test/scope.test.js`; `/api/meta` step list assertion in `test/server.test.js`. `test/css-tokens.test.js` fails until the new type has its tokens, icon and `[data-type]` rule in both themes and its colour pairs pass WCAG AA.
8. Run `npm test` and the `smoke-test` skill (add the step from the palette or a "+" point, configure it, preview).
